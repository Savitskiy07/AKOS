# Индивидуальное задание № 4.

**Вариант:** 16.

**ФИО:** Савицкий Александр

**Группа:** 252

Реализация на C11 для Linux с использованием TCP, независимых процессов
посетителей и нескольких динамически подключаемых наблюдателей.

## 1. Условие задачи

Картинная галерея имеет ограничение на общее число посетителей. Возле каждой
картины одновременно разрешено находиться не более заданного числа людей.
Посетители появляются через случайные интервалы. Если галерея заполнена,
посетитель ожидает разрешения вахтёра в очереди. После входа посетитель
осматривает все картины в случайном порядке либо по выбранной стратегии.
Если возле выбранной картины нет места, он ожидает. Осмотрев все картины,
посетитель выходит и освобождает место в галерее.

Входные данные: вместимость галереи, число картин, ограничения возле каждой
картины, число посетителей, интервалы появления, продолжительность осмотра
и стратегия выбора следующей картины. Для завершаемого решения в условии
рекомендуется 100–300 посетителей.

Отображаются прибытие, ожидание у входа, разрешение вахтёра, вход, выбор
картины, ожидание свободного места, начало и окончание осмотра, выход.

## 2. Программы и отображение сущностей модели

Разработаны три консольных приложения на C11 для Linux. Они используют TCP
и функции libc/POSIX; сторонние библиотеки не нужны.

**gallery_server** — один процесс, выполняющий роль вахтёра и координатора
ресурсов. Он хранит вместимость, очередь у входа, очереди у картин,
состояния посетителей и время окончания осмотра. Сервер не создаёт потоки:
он асинхронно обслуживает все соединения через poll и неблокирующие сокеты.

**gallery_visitor** — самостоятельный процесс одного посетителя. Каждый
посетитель открывает своё TCP-соединение, получает разрешение войти,
выбирает маршрут, запрашивает осмотр каждой картины и затем выходит.
Все процессы посетителей независимы; общей памяти между ними нет.

**gallery_observer** — самостоятельный клиент, отображающий целостное
состояние галереи. Число наблюдателей не зафиксировано; они могут находиться
на разных компьютерах и подключаться или отключаться во время моделирования.

Картины реализованы как ресурсы с отдельными ограничениями и очередями.
Создавать процесс на каждую картину не требуется: картина сама не совершает
действий, а её занятость меняют запросы посетителей. Вахтёр и посетители
представлены самостоятельными активными участниками, как требует условие.

Скрипт scripts/visitors.sh запускает отдельный процесс для каждого ID и задаёт
задержку появления. Он не выполняет координацию галереи. После подключения
все взаимодействия участников происходят по TCP.

## 3. Алгоритм моделирования

1. Посетитель ожидает заданную задержку появления, подключается и отправляет
   HELLO VISITOR с уникальным ID из диапазона 1..N.
2. Сервер регистрирует прибытие и ставит посетителя в FIFO-очередь на вход.
3. При наличии свободного места вахтёр выдаёт разрешение первому в очереди;
   сервер увеличивает число находящихся внутри и отправляет ENTERED.
4. Посетитель выбирает картину и отправляет VIEW. Для random заранее строится
   случайная перестановка всех картин; для sequential используется порядок 1..K.
5. Сервер ставит запрос в FIFO-очередь выбранной картины. При свободном месте
   он отправляет START и назначает время завершения осмотра.
6. По истечении времени сервер освобождает место, отмечает картину осмотренной
   и отправляет DONE. Посетитель выбирает следующую ещё не осмотренную картину.
7. Когда все картины осмотрены, посетитель отправляет LEAVE. Сервер проверяет
   полноту осмотра, освобождает место в галерее, отправляет BYE и закрывает связь.

Продолжительность осмотра определяет сервер, поэтому клиент не может зачесть
картину раньше окончания таймера. Используется CLOCK_MONOTONIC. Сервер
проверяет таймеры через poll и не останавливает обработку других клиентов
на время осмотра. Возможна небольшая задержка завершения из-за планирования ОС.

У каждой очереди монотонно возрастающие номера заявок. Из ожидающих выбирается
наименьший номер. Посетитель не удерживает место возле предыдущей картины,
когда запрашивает следующую. Циклическое ожидание мест у картин не возникает.

Один сервер последовательно применяет изменения состояния. При этом
посетители могут одновременно находиться внутри и осматривать разные картины:
логические периоды осмотра перекрываются. Потоки и блокировки для атомарности
счётчиков сервера не нужны.

## 4. Инварианты

- Число посетителей внутри не превышает вместимость галереи.
- Число осматривающих каждую картину не превышает её ограничение.
- Посетитель одновременно занимает место не более чем возле одной картины.
- Каждая картина засчитывается посетителю не более одного раза.
- Выход и разрыв связи освобождают ресурсы посетителя.
- Завершённым считается только посетитель, осмотревший все картины.

Каждый посетитель имеет одно состояние: ABSENT, ENTRY_QUEUE, INSIDE,
PICTURE_QUEUE, VIEWING, FINISHED или ABORTED. Осмотренные картины представлены
64-битной маской; отдельно обработан случай 64 картин, чтобы исключить сдвиг
на ширину типа. VIEW допустим только из INSIDE и только для неосмотренной
картины. LEAVE допустим только после заполнения маски.

После каждого шага сервер повторно подсчитывает значения по состояниям всех
посетителей и проверяет их через assert. Эти проверки включены в обычную
сборку. Интеграционные тесты дополнительно восстанавливают модель по журналу
независимо от внутренних счётчиков сервера.

## 5. TCP-протокол и асинхронность

Протокол текстовый: одна команда заканчивается LF. Сервер принимает только
печатные ASCII-символы в командах; сообщения о событиях содержат UTF-8-текст.
Максимальная длина входной строки ограничена буфером 1024 байта с учётом
завершающего нуля. Неизвестные команды, неверные числа, повторные ID,
преждевременный выход и повторный осмотр отвергаются сообщением ERROR.

Границы TCP-пакетов не считаются границами команд. На сервере и в клиентах
есть буферы для неполных строк и нескольких строк в одном чтении. Частичные
send/read, EINTR, EAGAIN и EOF обрабатываются. SIGPIPE не завершает процесс.
TCP_NODELAY устраняет нежелательные задержки коротких управляющих сообщений.

Соединения сервера неблокирующие. Каждое имеет отдельную исходящую очередь
с пределом 256 КиБ. При переполнении отключается только отстающий клиент.
Число чтений и приёмов соединений за один проход ограничено, чтобы обработка
одного соединения не вытесняла таймеры и остальных клиентов.

Данные выводятся через write и сетевые send/recv с файловыми дескрипторами.
snprintf и sscanf применяются для форматирования и разбора строк в памяти.

## 6. Реализация: наблюдатели

При подключении наблюдатель отправляет HELLO OBSERVER. Сервер помещает в его
очередь SNAPSHOT_BEGIN, ограничения и занятость картин, состояния уже
прибывших посетителей и SNAPSHOT_END. Оба маркера содержат одинаковый номер
последнего события. Отсутствующие посетители определяются как оставшиеся ID
из диапазона 1..N.

Снимок формируется внутри одного прохода однопоточного сервера, поэтому в него
не вклиниваются изменения модели. Затем в ту же очередь помещаются будущие
события с последовательными номерами. TCP сохраняет порядок переданных байтов.
Наблюдатель получает сначала целостное текущее состояние, затем все изменения
после него. История до подключения не воспроизводится.

Каждое событие содержит номер, время от запуска, тип, ID посетителя и картины,
актуальные счётчики, маску осмотренных картин и пояснение на русском языке.
Этого достаточно для наблюдения за системой без просмотра окон отдельных
посетителей и сервера.

Отключение наблюдателя закрывает только его сокет и освобождает его буфер.
Повторный запуск программы создаёт новое соединение и получает свежий снимок.
Наблюдатель не имеет права изменять модель: дополнительные команды отвергаются.
Медленный наблюдатель при переполнении своей очереди отключается и может
подключиться заново. Автоматическое переподключение не требуется: предусмотрен
повторный запуск программы пользователем.

В строках `EVENT` поле `seq` содержит номер события, `t_ms` — время от
запуска. ID 0 обозначает событие, относящееся ко всей галерее. Поле `seen` —
шестнадцатеричная маска: младший бит соответствует картине 1.
Полный журнал можно сохранить перенаправлением вывода наблюдателя,
подключённого до запуска посетителей.

## 7. Пользовательский интерфейс и запуск

Все сетевые программы требуют IP и порт через командную строку. Параметры
модели задаются серверу, параметры появления — каждому посетителю или скрипту.
Перечень параметров приведён ниже; также доступен вывод `--help`.

### 7.1. Быстрый запуск

Требуются Linux, GCC, Make и Bash. Python 3 нужен только для автоматических
тестов. Сторонних библиотек для трёх программ нет.

```bash
make
bash scripts/demo.sh 5050
```

Демонстрация запускает 100 посетителей, два наблюдателя, отключает второго и
запускает его повторно. Итог должен содержать:

```text
SUMMARY total=100 arrived=100 finished=100 aborted=0 remaining=0 status=complete
```

Журналы: `logs/demo/server.log`, `logs/demo/observer-1.log`,
`logs/demo/observer-2-reconnected.log`, `logs/demo/visitors/`.
В процессе выполнения их можно смотреть командой `tail -f logs/demo/observer-1.log`.

### 7.2. Запуск вручную: три терминала

**1. Сервер.** Он выполняет роль вахтёра и хранит состояние галереи:

```bash
./build/gallery_server --host 127.0.0.1 --port 5050 \
  --visitors 100 --capacity 10 --pictures 5 \
  --picture-capacities 2,3,2,1,2 \
  --view-min-ms 100 --view-max-ms 300 --strategy random --seed 16
```

**2. Наблюдатель.** Таких терминалов может быть несколько:

```bash
./build/gallery_observer --host 127.0.0.1 --port 5050
```

Для проверки переподключения нужно нажать Ctrl+C только в терминале наблюдателя, затем повторить команду: сервер
продолжит работу, а наблюдатель получит новое текущее состояние.

**3. Посетители.** Последние три аргумента задают минимальный и максимальный
интервал появления в миллисекундах и начальное значение генератора:

```bash
bash scripts/visitors.sh 127.0.0.1 5050 100 10 50 16
```

Скрипт запускает по отдельному C-процессу на каждого посетителя. Первый приходит
сразу; задержка последующих накапливается из случайных интервалов 10–50 мс.
Время запуска процессов добавляется к этой задержке, поэтому интервалы модели
приближённые. Логи посетителей сохраняются в `logs/visitors/`.

Один посетитель запускается так:

```bash
./build/gallery_visitor --host 127.0.0.1 --port 5050 --id 1 --arrival-ms 0
```

На один запуск сервера нужны **уникальные ID от 1 до N**, где N — его параметр
`--visitors`. Нельзя запускать одновременно одиночного посетителя с ID 1 и скрипт,
который повторно использует ID 1. Сервер ждёт всех N запланированных посетителей;
если запустить меньше, для остановки нужно нажать Ctrl+C в терминале сервера.

### 7.3. Запуск на разных компьютерах

На компьютере сервера:

```bash
./build/gallery_server --host 0.0.0.0 --port 5050 \
  --visitors 100 --capacity 10 --pictures 5 --picture-capacity 2
```

На компьютерах посетителей и наблюдателей вместо `127.0.0.1` необходимо указать реальный IP
сервера, например `192.168.1.10`. Адрес `0.0.0.0` используется только для
привязки сервера, не как адрес назначения клиента. TCP-порт 5050 должен быть
доступен между компьютерами. Необходимо собрать исполняемые файлы на каждой Linux-машине.

```bash
./build/gallery_observer --host 192.168.1.10 --port 5050
bash scripts/visitors.sh 192.168.1.10 5050 100 10 50 16
```

Если посетители запускаются с нескольких машин, необходимо разделить между ними уникальные
ID вручную. Скрипт всегда использует диапазон 1..N и рассчитан на один запуск
генератора посетителей. Наблюдатели ID не требуют.

### 7.4. Параметры сервера

| Параметр | Значение по умолчанию | Допустимые значения |
|---|---:|---|
| `--host` | обязательный | Числовой IP адрес привязки |
| `--port` | обязательный | 1..65535 |
| `--visitors` | 100 | 0..1000 |
| `--capacity` | 10 | 1..1000 |
| `--pictures` | 5 | 1..64 |
| `--picture-capacity` | 2 | 1..1000, одинаково для всех картин |
| `--picture-capacities` | не задан | Список положительных чисел, ровно по числу картин; заменяет общее ограничение |
| `--view-min-ms` | 200 | 0..60000 |
| `--view-max-ms` | 500 | 0..60000, не меньше минимума |
| `--strategy` | random | random или sequential |
| `--seed` | 1 | 0..4294967295 |

`random` — случайная перестановка всех картин, `sequential` — порядок 1, 2, …, K.
Ожидание у выбранной картины выполняется в FIFO-очереди: посетитель не держит
место возле предыдущей картины. Нулевые времена допустимы для быстрых тестов.

Лимит одновременных TCP-соединений сервера — 1024, включая ещё не представившихся
клиентов. Практическая граница также зависит от доступных файловых дескрипторов
и процессов Linux (`ulimit -n`, `ulimit -u`). Рекомендуемые в задании 100–300
посетителей проверены автоматическими сценариями.

## 8. Условия завершения

После прибытия всех запланированных посетителей сервер регистрирует
INPUT_CLOSED. Новые ID больше не принимаются; уже зарегистрированные
посетители из входной очереди продолжают посещение. При штатном выполнении
сервер завершает день после выхода всех N посетителей. Для N=0 он сразу
выводит успешную итоговую статистику.

При потере соединения посетитель переводится в ABORTED, а занятые им места
освобождаются. Если остальные посетители завершили посещение, сервер закрывает
день со статусом incomplete и кодом 2. Прерванный посетитель не приравнивается
к успешно завершившему. Повторное подключение рабочего клиента с тем же ID
не реализовано: это расширение выше целевого уровня 8.

Ctrl+C или SIGTERM на сервере приводит к сообщению INTERRUPTED и STOP для
подключённых клиентов. Сервер даёт до двух секунд на отправку накопленных
сообщений, затем закрывает оставшиеся дескрипторы. Он не ждёт бесконечно
отстающего наблюдателя. При прерывании remaining показывает число участников,
которые ещё не завершили посещение и не были отмечены прерванными до сигнала.

Если запущено меньше N посетителей или подключённый рабочий клиент перестал
посылать необходимые команды без закрытия TCP, сервер ожидает продолжения.
Такой сценарий можно закончить сигналом. Неограниченный по времени режим
моделирования не предусмотрен; он не обязателен для выбранного конечного дня.

Если клиент не отправил приветствие, сервер закрывает соединение через
5 секунд.

Коды выхода: `0` — успешное завершение; `1` — ошибка параметров или запуска;
`2` — ошибка протокола, разрыв связи или неполный рабочий день; `130` —
остановка сервера сигналом. Наблюдатель, остановленный непосредственно Ctrl+C,
завершается стандартным образом по сигналу.


Тесты используют настоящие TCP-соединения и отдельные исполняемые программы.

переподключение, медленный потребитель, граница 64 картин, некорректные команды,
фрагментация TCP, разрывы соединений и прерывание сервера.

| ASan + UBSan, без LeakSanitizer | 13 из 13 сценариев прошли, 2,392 с; диагностик нет |
| GCC -fanalyzer | Сборка всех трёх программ завершилась без диагностик анализатора |
| Демонстрация с 100 процессами посетителей | finished=100, aborted=0, remaining=0, status=complete |
| Повторное подключение наблюдателя в демонстрации | seq=250: прибыли 52, внутри 10, в очереди 40, завершили 2 |

Пример фактического снимка при повторном подключении наблюдателя:

```text
SNAPSHOT_BEGIN seq=250 total=100 capacity=10 pictures=5
  arrived=52 inside=10 queued=40 finished=2 aborted=0
  strategy=random seed=16
```

В примере одна длинная строка разбита для читаемости. Снимок не является
пустым начальным состоянием: уже идут посещения и есть очередь.
Затем наблюдатель получил все события до STOP reason=complete.

Автоматические сценарии:

1. 12 посетителей, вместимость 1, 4 картины, последовательный маршрут; проверка FIFO.
2. 100 посетителей, 7 картин с разными ограничениями, случайный маршрут,
   несколько наблюдателей, отключение и повторное подключение во время работы.
3. 300 посетителей, вместимость 20, 8 картин, нулевое время осмотра.
4. 64 картины, проверка старшего бита маски и полного осмотра.
5. Пустой рабочий день: 0 посетителей.
6. Команды, разделённые между TCP-чтениями, и несколько команд в одном отправлении.
7. Повторный ID, неверные ID, слишком длинная строка, нулевой байт в команде.
8. Повторный осмотр картины и выход до осмотра всех картин.
9. Разрыв связи при осмотре и в очереди; освобождение мест для остальных.
10. Наблюдатель, который перестаёт читать; второй наблюдатель и посетители продолжают работу.
11. SIGINT во время осмотра; завершение подключённого наблюдателя и клиента.
12. Недопустимые параметры командной строки.
13. Попытка наблюдателя отправить команду изменения модели.

Тестовый анализатор не доверяет счётчикам сервера: он заново строит состояния,
очереди и множество осмотренных картин по событиям. Для каждого события
проверяются вместимость, единственность места посетителя, отсутствие повторного
осмотра, FIFO и соответствие счётчиков. Поток каждого полностью работающего
наблюдателя сверяется с точным суффиксом серверного журнала после его снимка.

В сценарии на 300 посетителей одновременно запускается до 40 клиентских
процессов; по мере завершения запускаются следующие. Это полный рабочий день
из 300 посетителей, а не утверждение о 300 одновременных соединениях.
Демонстрационный скрипт отдельно запускает все 100 процессов с задержками
появления.

Сборка выполняется с -Wall -Wextra -Wpedantic -Werror. Дополнительно проведены
проверки AddressSanitizer и UndefinedBehaviorSanitizer и анализ GCC -fanalyzer.
Проверка утечек LeakSanitizer недоступна в данной среде: инструмент сообщает
о несовместимости с ptrace. Его исходный отказ сохранён в
test-results/leak-sanitizer-unavailable.txt. Для фактического запуска ASan/UBSan
использовано ASAN_OPTIONS=detect_leaks=0:halt_on_error=1. Отсутствие утечек по
LeakSanitizer не заявляется. На обычной Linux-машине make sanitize по умолчанию
включает проверку утечек.

Сетевые проверки проведены через реальные TCP-сокеты на одном Linux-хосте.
Запуск на разных физических компьютерах описан и поддерживается адресацией
программ, но в данной среде отдельно не проверялся.

## 11. Структура проекта

- `src/server.c` — сервер, модель, FIFO-очереди, таймеры, рассылка наблюдателям;
- `src/visitor.c` — один посетитель и выбор маршрута;
- `src/observer.c` — самостоятельная программа наблюдения;
- `src/common.c`, `src/common.h` — общие функции TCP, буферизация строк,
  разбор чисел, время и генератор случайных чисел;
- `tests/integration.py` — интеграционные тесты исполняемых программ;
- `tests/audit.py` — расширенные проверки требований уровня 8;
- `scripts/demo.sh` — демонстрация работы галереи и переподключения наблюдателя;
- `scripts/visitors.sh` — запуск отдельных процессов посетителей;
- `test-results/` — сохранённые сводки выполненных проверок;
- `Makefile` — сборка, тестирование и очистка результатов сборки;
- `.gitignore` — исключение автоматически создаваемых файлов;
- `README.md` — отчёт и инструкция по запуску (этот документ).

Каталоги `build/`, `build-sanitize/`, `build-analyze/` и `logs/` создаются
при сборке или запуске соответствующих сценариев и не требуют хранения в Git.
